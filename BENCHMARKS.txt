Benchmark reference correction (2026-10-28):
The performance baseline is the existing QUDA conjugate-gradient (CG) solve,
not the original Torch FP64 forward pass. The numbers below are operator
microbenchmarks only. None establishes a speedup over CG.
Solver comparisons must use identical gauge, RHS, boundary conditions, kappa,
initial guess, and target independently recomputed relative residual
||b-Ax||/||b||. Report total time to that residual, iterations/operator calls,
setup costs, and memory. For batching, compare equal numbers of solved RHS.
FP64 remains the numerical operator oracle, distinct from the CG performance
baseline. FP4 forward error alone is not a solver convergence criterion.
The existing replay bridge exposes quda_replay_solve_cg_d2d; its replay experiment
uses tolerance 1e-8 and maxiter 5000. A matched FP4 solver comparison is pending;
the new fused kernels currently implement forward applications only.

Measured CG reference (2026-10-28):
QUDA FP64 CG, same 56^3x96 gauge and seed-45 Gaussian RHS, zero initial guess:
  Setup with the existing 900-entry tuning cache: 15.4546 seconds.
  Warmed A*x median (three samples): 0.301918 seconds.
  Complete CG bridge call: 58.2625 seconds; internal invertQuda: 57.4228 seconds.
  153 iterations; independently recomputed ||Ax-b||/||b|| = 9.25048e-9.
One complete solve measured, not a multi-run median. The bridge's host staging
is included in call wall time. These measurements supersede using the original
Torch FP64 forward as the performance baseline. No Torch/FP4 solve has yet
demonstrated the same residual and hence no solve speedup is established.

Ideas implemented:
1. Cached color matrices and sparse spin permutations.
2. Native E2M1 color contraction using Triton tl.dot_scaled.
3. Fused gathers, eight direction products, projection and sums per Dslash.
4. Two sites packed into one block-diagonal tensor-core tile.
5. Three-product FP4 correction: Ahi*Bhi + Alo*Bhi + Ahi*Blo (omits Alo*Blo).
6. Batched right-hand sides to fill tensor-core columns.
7. Fused FP16 control to distinguish fusion from precision benefits.

Precision and validation:
Emitted PTX contains mma.sync ... mxf4nvf4 ... e2m1 tensor-core instructions.
FP4 operands use FP8 power-of-two scales, FP32 hardware accumulation and FP32
external state. Gauge caches remain uncompressed. This is NOT all-FP4 storage.
Quantization makes the approximate map nonlinear: it is not exactly the linear
SPD physical operator. Fused modes deliberately reject autograd; the original
Torch network and ordinary cached modes retain it. No silent fake gradient.

validate_fp4.py checks an independent Torch quantize/dequantize implementation
against fused kernels: both parities, dagger/non-dagger, periodic/antiperiodic
time, batches 1/4/8, one/three-product variants. All 48 checks passed with zero
relative disagreement. Stale-cache guard also passed. This validates the chosen
quantized algorithm, not its suitability for HMC. Full-size testing exposed a
32-bit address overflow in paired-site packing; offsets now use 64-bit math.

Method:

Container digest sha256:6e8ccc607fc2a51e3741667b86316a0889418ba8b78ed0ba96e8d282b648a7a6.
One warmup, three synchronized wall times, median reported. Setup and compilation
excluded; setup is recorded separately in JSON. Gauge changes require rebuilding

the original network and reconstruct the desired cached execution mode.
